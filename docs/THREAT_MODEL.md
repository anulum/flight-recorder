# Tooling trust boundaries

Current assets are maintained source, exact metadata/schema/lock identities and scoped infrastructure reports. Reviewed executable policy and its independently pinned schema are trusted. Received JSON cannot choose an executable, repository identity, plugin or weaker policy.

The implemented input boundary refuses duplicate keys, nonfinite values, invalid UTF-8, unpaired surrogates, oversized files and linked/nonregular inputs. Fixed authored diagnostics avoid echoing confidential values. Accepted metadata precedes exclusive output creation; verification never replaces an inventory.

The tooling assumes a stable ordinary local filesystem and reviewed environment. It does not sandbox hostile concurrent filesystem changes, operating-system compromise or power loss. Static checks do not establish real capture, instrument fitness, surviving checkpoints, complete history or permitted offload.

Future segments require actual pack/layout/unit/timebase binding, canonical raw bytes, valid event and segment sequences, actual independent anchors and complete budget accounting. Missing predecessor bytes, unknown epochs, gaps and quarantined conflicts remain visible. Capture and sharing permissions are distinct; no export silently expands either scope. Hash continuity is evidence about retained bytes, not proof that every physical event was recorded.
